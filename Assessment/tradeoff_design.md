# Assessing tradeoff design

评价 Harness 设计时，先明确它要解决的实际任务和风险，再判断新增结构是否改善了 Agent 行为，以及改善是否值得承担阅读、执行、人工复核和维护成本。

## 1. 设计比较任务

为同一个任务设置不足的指导或控制，以及认真、准确、较高结构的对照方案。高结构方案应具有真实用途，足以暴露收益和负担。学习者最后根据证据选择适合当前条件的设计，必要时再次运行验证。

不同强度的方案使用同一组学习视角，例如信息可达性、任务粒度、完成证据、风险控制和协作成本。每个视角观察结构强度如何改变结果。

| 设计问题 | 指导或控制不足的风险 | 结构过多的风险 | 需要比较的证据 |
|---|---|---|---|
| 项目导航 | 猜测、无关探索、依赖口头说明 | 重复、过时、阅读路径过长 | 首批读取路径、事实准确性、不确定点、复核成本 |
| 任务和范围 | 同时开展多个行为、顺手扩大修改 | 任务过碎、阻止必要依赖处理 | 实际需求、diff、范围决策、阻塞及拆分成本 |
| 权限和审批 | 高风险状态变化缺乏检查 | 正常验证停滞、审批疲劳 | 操作后果、可逆性、停止记录、审批负担 |
| 验证和完成 | 缺少真实业务证据、过早完成 | 检查昂贵、重复、难以复跑 | 实际命令/结果、业务不变量、遗漏和新增成本 |
| 状态和交接 | 下一会话无法恢复事实和下一步 | 信息噪音、重复维护、状态冲突 | 接手演练、证据路径、口头补充和维护负担 |

## 2. 保留比较条件

记录任务、行为范围、起始源码或状态、Agent/模型、工具权限、预算、提示词、人工帮助和运行顺序。列出主动改变的因素及可能影响解释的差异。

同一仓库、同一任务内的对照更容易解释。跨项目的原始耗时、文件数和文档量具有不同含义。对照中同时改变了多个因素时，应报告可观察结果与合理机制，明确单个因素的效果尚未被隔离。

保留每轮完整输入输出、交互记录、执行结果、diff、环境信息和异常。缺失的时间、命令、运行或人工帮助写明未记录。

## 3. 判断设计推理

评价者需要从证据中恢复以下推理：

1. 学习者预测了什么行为变化，为什么当前机制会产生该变化？
2. 哪些日志、diff、结果或接手表现支持、限制或反驳预测？
3. 哪些结构改善了行为，哪些引入成本，哪些没有可见效果？
4. 为什么选择保留、放松、合并或移除某项结构？
5. 什么任务条件或新证据会使学习者修改该选择？

可以出现改善、未变、恶化或阻塞。设计判断的质量取决于它如何处理这些证据。若任务受环境阻塞，仍可分析已展示的诊断与调节，同时保留对设计效果的结论边界。

## 4. 连接 K/M/R/I

| 构念 | 在设计比较中的观察对象 |
|---|---|
| K | 学习者是否正确应用当前任务教授的方法 |
| M1–M4 | 学习者是否规划、发现信号、评价证据，并依据风险或结果调整策略 |
| R | 设计选择是否有任务条件、机制理由和边界或修订触发条件 |
| I | 是否从当前观察推导可迁移机制，并提出未来测试或适用边界 |

一次决策可以为多个构念提供证据，但每项主张需要分别说明理由。工件正确性可以证明系统层面的结果；学习者归因需要交互中可见的选择、评价、修改或运用。使用 [profile](profiles/harness_engineering/PROFILE.md) 和 [session skill](session_evidence/SKILL.md) 作具体判断。

## 5. 报告范围

分别说明任务表现、设计取舍和 K/M/R/I 证据。保留来源依赖、冲突、观察机会和覆盖局限。数字评分仅使用提供的任务量规；一般原则本身不定义分数、权重或总评等级。多任务、独立评分者一致性或因果学习效果需要相应研究证据支持。
